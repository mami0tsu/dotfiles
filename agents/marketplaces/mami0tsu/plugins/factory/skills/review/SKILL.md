# Review

## 入力

設定の絶対パス、対象と目的、対象スキル名、内容と根拠、対象の参照と版を受け取る。
候補と調査結果では research から単一 `output` と調査記録の参照と版を引き継ぎ、登録済みの調査結果ではアイデア、成果物ではタスクの参照も受け取る。
成果物では、タスクの単一 `output` と記録済みの成果物 `id`、`url`、`revision`、受け入れ条件、検証結果を使う。
他のスキルからも同じ入力で呼び出せる。
対象や記録先が不明なら推測せず `wait` を返す。

## 手順

1. 導入済みスキルのカタログから factory の `init` の実パスを解決し、次を直接実行する。
   標準出力の既定値補完済み JSON を使い、CUE 不在は `wait`、設定不正は `error` とする。
   設定がなければパスを返して保留し、このスキルから初期化しない。

   ```sh
   cue export <init-dir>/assets/config.cue json: /absolute/path/factory.json --out json
   ```

2. 候補と調査結果は research から引き継いだ `outputs[output]`、成果物はタスクの `outputs[output]` を使う。
   管理対象には調査結果の `roles.ideas`、成果物の `roles.tasks` を使う。
   `output` が未指定、複数値、未知のキー、目的や受け入れ条件との矛盾なら保留する。
   同名キーの設定先を含め、記録済みの操作先、リポジトリ、対象の `id` と `url` が一致するか確認する。
   不一致なら別の出力先へ切り替えず保留する。
3. 選んだ binding の `adapter` を `adapters` で引き、`source: builtin` は factory、`external` は指定 `plugin` の `skill` をカタログから解決する。
   実パスの SKILL.md を読み、必要な役割、操作先の種類、操作、ツール、権限への対応を確認する。
   プラグインをまたぐ相対パスやサービス名の分岐を使わず、不在や未対応なら保留する。
   各依頼には設定パス、`role`、`target`、`operation`、`input` を渡し、更新には安定した `key` を付ける。
4. 候補と調査結果は同じ出力先の `staging/get` で調査記録の本文と版を読み、登録済みなら `ideas/get` で管理対象も確認する。
   成果物は `tasks/get` と同じ出力先の `artifacts/get` で最新の対象を読む。
   新しいレビュー結果の ID や未登録候補のアイデア ID は要求しない。
   版が変わっていれば、同じ対象であることを確認して最新 `revision` へ切り替え、新しくレビューする。
   古い版の AI 判定や人間の判断を流用しない。
5. 対象スキル名が設定の `loop.skills` に存在することを確認し、正規化済みの `reviewers[対象スキル名]` を使う。
   常に `reviewers.review` を使うことや、明示された空配列を `default` で上書きすることはしない。
   AI レビューは現在の担当が行い、設定レビュアーは人間への依頼先として使う。
   候補の AI 判定を人間の宛先解決で止めない。
   次のケースで必要な根拠を読み、未確認の事実を判定根拠にしない。

   | ケース | 確認する内容 |
   | --- | --- |
   | 候補 | 根拠、`ideas/list` で取得した既存アイデアとの重複、登録可否を確認する。重複の取得範囲が不足すれば保留する。 |
   | 調査結果 | 判断に必要な根拠と不足、結論が根拠から導けるかを確認する。 |
   | 成果物 | 受け入れ条件と対象版の内容、検証結果、未検証範囲を確認する。 |

6. [結果テンプレート](assets/result.md)に対象版、観点、指摘、AI 判定を記す。
   AI 判定は `pass`、`revise`、`hold` とし、人間の採用や承認として扱わない。
   人間の判断は、アダプターで読み返した明示的な根拠について判断者、日時、URL、対象版を照合し、未確認なら未承認とする。
   変更提案のレビューに限らず、管理対象のコメント等にある人間の判断も同じ条件で確認する。
7. 候補は同じ出力先の `staging/save` で元の調査内容を保持して結果を追記し、調査結果は `ideas/comment`、成果物は `tasks/comment` に対象の参照と版とともに記録する。
   安全に記録できない場合は保留し、成果物そのものや変更提案の head を更新しない。
   レビュー対象の `reviewed` と保存後の `record` は別々の `id`、`url`、`revision` として返し、保存で変わった版に旧判定を適用しない。
   `key` は対象の参照、ケース、対象スキル名、対象版から安定して作り、同じ対象への更新を直列化する。
   書き込み前に最新の対象と版、既存結果の key を再照合し、同じ結果は再利用する。
   版が変わったら手順4へ戻り、結果不明の書き込みは繰り返さず保留する。
8. 候補の AI `pass` は人間の採用を要求せず `success` として、同じ `output`、調査記録、結果を register へ渡す。
   AI `revise` は `success` として修正条件を返し、`hold` は `wait` として不足を返し、人間へ無条件に依頼しない。
   登録済みの調査結果と成果物の AI `pass` で必要な人間の判断がなければ、同じ版と設定レビュアーを示して依頼する。
   変更提案は同じ出力先の `changes/request-review`、それ以外は対応する管理先へのレビュー依頼コメントを使う。
   依頼方法、宛先、権限、既存依頼を確認し、未対応や宛先不足なら理由を記録して `wait` とする。
   依頼後も人間待ちは `wait` とし、再開に必要な対象版と記録先を返す。
   アダプターの `wait` と `error` は引き継ぎ、記録と依頼の結果を再取得して確認する。

出力には `status: success | wait | error`、`reviewed` と `record`、AI 判定、人間の判断根拠または待機理由を返す。
`success` はレビュー処理の完了だけを表し、採用や承認を意味しない。
