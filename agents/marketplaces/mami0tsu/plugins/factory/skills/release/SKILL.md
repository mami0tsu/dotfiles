# Release

## 入力と設定

設定の絶対パス、タスクの `id` と `url`、単一の `output`、記録済み binding、引き継いだ成果物の `id`、`url`、`revision`、人間の承認根拠、既存の実行記録を受け取る。
既存の権限と明示された人間の指示を守り、確認済みの許可範囲だけで操作する。
設定や CUE がなければ `wait`、次の検証に失敗したら `error` を返す。
`<factory-dir>` はこのスキルと同じプラグインの実在ディレクトリに置き換え、標準出力の既定値補完済み JSON を使う。

```sh
cue export <factory-dir>/skills/init/assets/config.cue json: /absolute/path/factory.json --out json
```

1. `roles.tasks` と、タスクが選んだ `outputs[output]` の binding を使う。
   `source: builtin` は同じ factory の指定スキル、`source: external` は指定 `plugin` と `skill` を導入済みカタログの実在パスで解決し、手順を読む。
   プラグインを跨ぐ相対パスやサービス名による分岐は使わない。
   必要な `role`、`target.kind`、`operation`、接続ツールの実際のスキーマと権限を確認し、不足や未対応は `wait` を返す。
2. アダプターには設定パス、`role`、`target`、`operation`、`input` と、書き込みには安定した `key` を渡す。
   `input` へ対象の正本参照、`output`、期待する `revision` と確認根拠を含める。
   `staging`、`artifacts`、`changes` は同じタスク出力先の論理上の役割とし、別の binding や公開先を作らない。
   `comment.subject` は現在のアイデア、タスク、固定 URL のいずれかから解決し、対象の `id` と `url` を渡す。

## 承認と現在値の照合

1. 管理先アダプターの `tasks/get` でタスクを再取得する。
   記録された `output` が未指定、未知、複数値、受け入れ条件と矛盾する場合は `wait` を返す。
   設定の同じキーの `adapter` と `target` を記録済み binding、成果物の正本参照と照合する。
   保存先、コメント先、リポジトリ、base が変わっていれば切り替えず保留する。
   変更提案は1タスク1リポジトリ1 PRを守る。
2. 出力先アダプターの `artifacts/get`、変更提案なら `changes/get` で現在の成果物を取得する。
   引き継いだ `id`、`url`、`revision` と一致しなければ保留する。
   親アイデアや依存先がある場合は設定の管理先から再取得し、取消、依存の未完了、不明な関係があれば保留する。
3. 人間の承認記録を原文から確認する。
   判断者、日時、根拠 URL、承認状態、対象の `id`、`url`、`revision` を現在値と照合し、取消や変更要求も確認する。
   外部のタスクコメント等に明示された承認も、該当アダプターの読み取り手順で原文と発言者を検証して扱う。
   AI のレビュー結果やレビュアーの設定を人間の承認とみなさない。
   承認根拠が不明、対象版が異なる、必要な承認が揃わない場合は `wait` を返す。
4. 現在のタスク状態が `states.tasks.release-ready` と一致し、人間がリリース可能と判断した根拠も確認する。
   状態名だけで判断を代行せず、承認と状態の両条件が揃うまで保留する。
   このスキルで承認を投稿したり、タスク状態や Draft を変更して条件を作ったりしない。

## リリースと再実行

1. 同じタスクと成果物への操作を直列に行う。
   タスク、`output`、成果物、承認対象版、操作から安定した `key` を決め、既存の実行記録とアダプターの結果を照合する。
   同じ結果が確認できれば再利用する。
   複数一致、取得範囲の不足、書き込み結果不明なら再送せず `wait` を返す。
2. 書き込みの直前にタスク状態、設定の binding、承認の有効性、対象の期待版を再照合し、次の操作へ渡す。

   - `file` と `comment` は `artifacts/get` で保存済みの内容と版を確認する。
     同じ保存先に承認版があれば同じ参照を使い、コピーやコメントを増やさない。
     承認された保存操作が必要な場合だけ `artifacts/save` に既存 ID と期待版を渡す。
     保存で内容や版が変わる場合は新たな承認を待つ。
     追加公開に必要な操作をアダプターが扱えなければ保留する。
   - `change` は `changes/approval` に検証済みの人間の承認根拠を渡す。
     現在の head、base、必須レビュー、チェック、競合、取り込みポリシーを再確認する。
     許可済みの方式で `changes/merge` に期待する head revision と両条件の根拠を渡す。
     外部での承認は接続先の必須条件を代替しない。
     Draft、不一致、権限不足は保留する。
     既に同じ変更提案が取り込み済みなら取り込み結果を再利用する。

3. 操作後はアダプターで対象を再取得し、承認した成果物、リリース先、結果の `id`、`url`、`revision` を検証する。
   承認対象版と保存後の版や merge commit は区別して記録する。
   途中まで成功した場合も確認済み参照を残し、不明部分を再実行しない。
4. [結果テンプレート](assets/result.md)で `success | wait | error`、確認済み項目 `items`、理由 `reason`、再開条件を返す。
   管理先の `tasks/comment` で同じ key の記録を再利用または更新し、元アイデア、タスク、`output`、成果物、承認、リリース先と結果を対応付ける。
   記録の保存に失敗してもリリース操作を繰り返さず、確認済みの結果を添えて `wait` を返す。
   次の処理スキルは起動せず、呼び出し元へ返す。
