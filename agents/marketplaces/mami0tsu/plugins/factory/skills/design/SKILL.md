# Design

設定の絶対パス、タスクの `id/url`、再開時の記録を受け取る。
要求、調査結果、受け入れ条件、既存設計、修正時のレビュー指摘はタスクの正本から確認する。
実装、タスク分割、人間の承認代行、merge は行わない。

## 設定と対象の確認

1. 開始時に次を直接実行し、標準出力の既定値補完済み JSON を使う。
   `<init-dir>` は同じプラグインの `skills/init` の実パスに置き換える。

   ```sh
   cue export <init-dir>/assets/config.cue json: /absolute/path/factory.json --out json
   ```

   不正な設定は `error`、CUE、設定、必要な入力の不足は `wait` を返す。
2. `roles.tasks` と元アイデアの参照に使う `roles.ideas` の adapter を `adapters` から解決する。
   `source: builtin` は factory、`external` は指定 `plugin` の `skill` を、利用可能なスキルカタログから実パスへ解決して読む。
   必要な既存手順も同様に解決し、プラグインをまたぐ相対パスは作らない。
   `tasks/collection:get,comment` と、元アイデアの参照に必要な操作への対応と権限を確認する。
   未対応、不在、権限不足は保留し、別の adapter へ切り替えない。
3. task adapter の `get` で正本の本文、状態、親、依存関係、版を取得する。
   `work: design`、`states.tasks.ready`、依存先の完了、取消や撤回がないことを確認する。
   元アイデアの要求と合意内容も正本で照合し、修正依頼の対象版が不明、依存未完了、取消済みなら保留する。
4. タスクの単一 `output` を `outputs` と照合し、adapter と target を確定する。
   未指定、複数値、未知のキー、受け入れ条件との矛盾は保留する。
   同じ解決手順で出力先のスキルを読み、`staging/<選択kind>:get,save` の対応と権限を確認する。
   記録済みの `destination` と対象や成果物の `id/url/revision` を照合し、同名キーの設定先が変わっていれば保留する。
   コメント先は `subject` のアイデア、タスク、固定 URL から解決し、対象の `id/url` を入力へ渡す。
   `repositories` やアイデア管理先を作業先と推測しない。

## 必要な設計の作成

既存設計を読み、合意済みの範囲と受け入れ条件に必要な粒度だけを選ぶ。
導入済み `dev` の `design-flow` にある要求と受け入れ条件の整合確認を再利用し、文書には利用可能な日本語作成スキルを適用する。
このタスクで確定済みの出力先や合意内容を再選択せず、[最小テンプレート](assets/design.md)を使う。

| ケース | 記す内容 |
| --- | --- |
| 要求整理 | 目的、対象範囲、制約、受け入れ条件と確認方法を整理する。矛盾や不足を未解決事項にする。 |
| 構成設計 | 必要な構成要素と責務、境界、データの流れ、選択理由を記す。 |
| 詳細設計 | 変更箇所の入出力、データ、失敗時の挙動、検証方法を必要な範囲で具体化する。 |
| レビュー修正 | 指摘と対象版を照合し、同じ成果物を更新する。指摘ごとの対応、判断理由、再確認結果を残す。 |

必要なら複数ケースを組み合わせる。
実行した検証と机上確認を区別し、未解決事項で設計を確定できなければ不足と再開条件を記録して保留する。

## 保存と引き渡し

1. 同じタスクと出力先への更新を直列化し、タスク、`output`、用途から決めた安定した `key` を再実行でも使う。
   adapter には設定パス、`role`、同じ `target`、`operation`、`input`、`key` を渡す。
   既存成果物は `staging/get` で記録済み `id/url/revision` と現在版を照合し、修正指摘がその版に対応することを確かめる。
   新規保存では存在しない ID の `get` を要求せず、adapter の key 照合で既存結果を探し、一致する結果を再利用する。
2. 書き込み直前にタスクの状態、依存関係、対象と版を再確認し、`staging/save` で指定の一時保管先へ保存する。
   ファイルの書き込み可能な ref、変更提案の base/head など必要な入力が未確定なら保留する。
   保存後に再取得し、内容と対象、成果物の `id/url/revision` を確認する。
   成否不明や競合では再投稿せず保留し、次回は既存結果から照合する。
3. task adapter の `comment` で、設計の要点、`output`、解決済み target、対象と成果物の `id/url/revision`、確認結果、未解決事項を同じ key に関連付けて残す。
   記録失敗時は保存済み参照を返して保留し、成果物を作り直さない。
4. `next: review` と、設定パス、タスク、受け入れ条件、同じ `output/target`、対象と成果物の参照と revision を呼び出し元の loop または人間へ返す。
   review はここで起動せず、呼び出し元が処理枠を管理する。
   カタログに factory の `review` がなければ、引き渡す入力と理由を残して保留する。
   レビュアーの判断を承認へ読み替えず、人間の承認待ちも記録して処理を終える。

結果は `status: success | wait | error`、タスクと出力先、対象と成果物の参照、理由、次の処理を返す。
`success` は設計の保存とレビューへの引き渡しを示し、人間による承認を意味しない。
